Asynchronous job pattern

The flow creates a job, returns its ID to the app, and continues OCR and prompt processing while the app polls the job status.

Design boundary: this page documents the pattern, not a production export. It contains no connection names, site addresses, IDs, credentials, or live data.

Build sequence

  1. Create the Power Apps V2 trigger.
    Add optional FMP/FIA files, document flags, a friendly organization label, and an optional notification address.
  2. Generate a correlation ID.
    Normalize the friendly label and append a new GUID. Do not expose environment identifiers.
  3. Create the queued job.
    Write the job ID, status, and start time to a least-privilege job store.
  4. Return the job ID immediately.
    The app can navigate to Results and poll the job record.
  5. Set the job to Running.
    Place processing in a dedicated scope with a separate failure scope.
  6. OCR and chunk the FMP.
    Run plan-period and AAC evidence prompts into separate arrays, then run one final prompt for each metric.
  7. OCR and chunk the FIA.
    Run commercial-volume, IAC, and RAC evidence prompts into separate arrays, then consolidate each metric separately.
  8. Update the completed job.
    Write the five candidate results, completion time, and Completed status.
  9. Send an optional minimal notification.
    Direct the requester back to the approved app; do not attach source documents or unnecessary extracted content.

Consistent overlapping chunks

step = chunkSize - overlap
chunkCount = ceiling(textLength / step)

for index from 0 to chunkCount - 1:
    start = max(0, index * step)
    length = min(chunkSize, textLength - start)
    chunk = substring(text, start, length)

Overlap helps preserve a metric label at the end of one chunk and its value at the beginning of the next. Choose size and overlap through approved model-limit and quality testing.

Keep separate evidence arrays. Plan period, AAC, volume, IAC, and RAC should never share one collection. Separate arrays make the final prompt input traceable and avoid cross-metric contamination.

Controlled failure path

Configure a failure scope to run when processing fails, times out, or is skipped unexpectedly. Update the job to Failed, record the completion time, and store only a sanitized support message.

Status = Failed
Error  = "Processing could not be completed. Record the job ID and use the approved support channel."
Do not expose connector responses, OCR text, stack traces, internal URLs, or tokens in user-visible errors.
